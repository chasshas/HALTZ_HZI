# HALTZ repository layout v1 (provisional)

Status: draft, rev 3, 2026-11-20. Goes with architecture-v1.md and wiring-v1.md.
Rev 2: both ESP32 projects use framework = espidf, so the shared library is pulled in as an ESP-IDF component (EXTRA_COMPONENT_DIRS) instead of a PlatformIO symlink library. Added per-project settings.
Rev 3: checked ESP-IDF's known problems with the N16R8's large flash/PSRAM. Added XIP from PSRAM, a module check before first flash, and a pitfalls list (cpu-s3 section).
Goal: separate firmware projects per board, but one repository and one VS Code window, with the data-interchange code written once and shared.

## Common settings (repo root)
- .clang-format and .editorconfig: one code style for every C/C++ project.
- Warnings on everywhere: -Wall -Wextra.
- Shared code is written to C11 (accepted by every compiler here), with `extern "C"` guards so the C++ I/O firmware can include it. Each firmware keeps its toolchain's default language standard.
- haltz.code-workspace recommends the extensions: PlatformIO IDE, Raspberry Pi Pico, C/C++, CMake Tools, Python.
- .gitignore: .pio/, build/, sdkconfig.* generated by PlatformIO except the committed defaults, tools/.venv/.

## shared/haltz_proto: CMakeLists.txt in three modes
```cmake
if(ESP_PLATFORM)
  # built as an ESP-IDF component (cpu-s3, io-esp32)
  idf_component_register(SRCS src/packet.c src/crc8.c src/msgs.c
                         INCLUDE_DIRS include)
else()
  # Pico SDK or a plain PC build
  add_library(haltz_proto STATIC src/packet.c src/crc8.c src/msgs.c)
  target_include_directories(haltz_proto PUBLIC include)
  set_target_properties(haltz_proto PROPERTIES C_STANDARD 11)
  option(HALTZ_BUILD_TESTS "Build PC unit tests" OFF)
  if(HALTZ_BUILD_TESTS)
    add_executable(haltz_proto_tests test/test_main.c)
    target_link_libraries(haltz_proto_tests haltz_proto)
  endif()
endif()
```
PC tests: `cmake -S shared/haltz_proto -B build-host -DHALTZ_BUILD_TESTS=ON` then build and run. Needs a PC compiler (gcc/clang; on Windows WSL or MinGW).
Rules for the shared code: see "Rules" below.

## firmware/cpu-s3 (PlatformIO, ESP-IDF, C)

### Before the first flash: check which module is on the board
- Read the metal can: "ESP32-S3-WROOM-1 ... N16R8" = quad flash at 3.3 V + octal PSRAM. That's what the settings below are for.
- If it says WROOM-2, or the code ends in V (N16R8V, N32R8V): octal flash at 1.8 V. That needs different settings (octal flash on); the settings below would boot-loop.
- Never change the flash-voltage eFuse (VDD_SPI). It's permanent, and the wrong level stops the flash working.
- After the first flash, the boot log should show 16 MB flash and an 8 MB octal PSRAM found. That's step 3 of the setup order.

### platformio.ini
```ini
[env:cpu]
platform = espressif32 @ 6.13.0      ; pin it; 6.13.0 ships ESP-IDF 5.5.3
board = esp32-s3-devkitc-1
framework = espidf
board_build.flash_mode = qio
board_upload.flash_size = 16MB
board_upload.maximum_size = 16777216
board_build.partitions = partitions.csv
monitor_speed = 115200
monitor_filters = esp32_exception_decoder
upload_port = COMx                   ; the S3's own port
monitor_port = COMx
```
The generic esp32-s3-devkitc-1 board file assumes less flash and no PSRAM, so the flash size must be overridden here, and PSRAM must be enabled in sdkconfig.

### Root CMakeLists.txt (EXTRA_COMPONENT_DIRS before include)
```cmake
cmake_minimum_required(VERSION 3.16)
set(EXTRA_COMPONENT_DIRS ${CMAKE_CURRENT_LIST_DIR}/../../shared/haltz_proto)
include($ENV{IDF_PATH}/tools/cmake/project.cmake)
project(haltz_cpu)
```
src/CMakeLists.txt: `idf_component_register(SRCS "main.c" ... INCLUDE_DIRS "." REQUIRES haltz_proto esp_psram)`.

### sdkconfig.defaults
Committed; PlatformIO generates sdkconfig.cpu from it. Delete sdkconfig.cpu after changing the defaults.
```
CONFIG_ESPTOOLPY_FLASHSIZE_16MB=y
CONFIG_ESPTOOLPY_FLASHMODE_QIO=y
CONFIG_SPIRAM=y
CONFIG_SPIRAM_MODE_OCT=y
CONFIG_SPIRAM_SPEED_80M=y
CONFIG_SPIRAM_USE_CAPS_ALLOC=y
CONFIG_SPIRAM_XIP_FROM_PSRAM=y
CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ_240=y
CONFIG_FREERTOS_HZ=1000
```
- SPIRAM_USE_CAPS_ALLOC: PSRAM is only used when asked for (heap_caps_malloc with MALLOC_CAP_SPIRAM). Plain malloc() stays in internal RAM, so drivers never get a PSRAM buffer by surprise.
- SPIRAM_XIP_FROM_PSRAM: the app's code and read-only data are copied into PSRAM at boot. Then writing to flash (saving files, NVS) no longer switches off the caches, so the VM and PSRAM keep working during a save. Costs roughly the app size in PSRAM, which 8 MB can spare. (Older ESP-IDF names: SPIRAM_FETCH_INSTRUCTIONS + SPIRAM_RODATA.)
- SPIRAM_SPEED_80M: the safe speed for octal PSRAM. Faster modes are experimental.
- Optional tuning later: larger data cache (64 KB, 64-byte lines) speeds up PSRAM access.
- Bluetooth stays off on the S3 (the I/O board does Bluetooth).
- partitions.csv: nvs, phy_init, one app partition (~4 MB, no OTA for now), and a "storage" data partition with the rest of the 16 MB for the filesystem (KEY-cartridge programs, settings). Filesystem component (LittleFS) gets added at bring-up step 7.

### Known ESP-IDF pitfalls with the N16R8 (and how HALTZ avoids them)
| Pitfall | What happens | HALTZ rule |
|---|---|---|
| Wrong flash/PSRAM mode for the module | Boot loop, or PSRAM not found | Check the module marking first; quad flash + octal PSRAM for WROOM-1 N16R8 |
| GPIO35-37 used for wiring | Crashes: they're the octal PSRAM bus | Never wired (see wiring-v1.md) |
| Flash write while code touches PSRAM | Without XIP, caches are off during flash writes; PSRAM access then crashes or the other core stalls | XIP from PSRAM on |
| PSRAM settings put in build_flags (`-D CONFIG_...`) | Ignored with framework = espidf | All CONFIG_ settings go in sdkconfig.defaults |
| `-mfix-esp32-psram-cache-issue` copied from forum posts | That flag is for the original ESP32 only | Not used |
| DMA from PSRAM | Works on the S3 but slow, needs cache sync and alignment; DMA descriptors can't live in PSRAM | SPI/UART DMA buffers always internal (MALLOC_CAP_DMA) |
| Task stacks in PSRAM | Not allowed by default; risky during flash writes | All task stacks internal |
| PSRAM is slower than internal RAM | Interpreter loop gets slower if its hot data is in PSRAM | Active VM memory (64 KB) and VM registers in internal RAM; PSRAM for files, asset ROM, extra programs |
| Early S3 chip-revision cache bug | Rare cache errors | Worked around automatically in ESP-IDF 5.2+ (we use 5.4.2 / 5.5.3) |

## firmware/io-esp32 (PlatformIO, ESP-IDF + Arduino + Bluepad32 template, C++)
- Start from ricardoquesada/esp-idf-arduino-bluepad32-template, copied into firmware/io-esp32 (copy the files, or add it as a git subtree; don't leave a nested .git inside the repo).
- Keep the template's own platformio.ini platform pin and its sdkconfig. It requires ESP-IDF 5.4.2 and already has Bluetooth (BLE + Classic) and Arduino configured. Don't upgrade it to match cpu-s3; the two ESP32 projects may use different platform versions.
- Use the template's plain ESP32 environment (DevKit V1 = esp32dev); delete the other boards' environments to avoid building the wrong one.
- Add the same `set(EXTRA_COMPONENT_DIRS .../shared/haltz_proto)` line to its root CMakeLists.txt, and `REQUIRES haltz_proto` (or PRIV_REQUIRES) in its main component.
- Set upload_port / monitor_port to the DevKit V1's port.
- Language: C++ for the firmware (Bluepad32's Arduino API is C++); shared headers are included through their extern "C" guards.
- The DevKit V1 has no PSRAM, so none of the PSRAM pitfalls apply here.

## firmware/gpu-pico (Pico SDK, C)
Create with the Raspberry Pi Pico extension: New C/C++ project, board Pico 2 W, latest SDK 2.x, stdio over UART on (UART0 on GP0/GP1 = the debug probe's UART wires), stdio over USB off, no wireless features, debugger = DebugProbe (CMSIS-DAP). Keep the lines the extension adds at the top of CMakeLists.txt.
Key CMakeLists.txt lines:
```cmake
cmake_minimum_required(VERSION 3.13)
set(PICO_BOARD pico2_w CACHE STRING "Board type")   # before pico_sdk_import
include(pico_sdk_import.cmake)
project(haltz_gpu C CXX ASM)
set(CMAKE_C_STANDARD 11)
set(CMAKE_CXX_STANDARD 17)
pico_sdk_init()

add_subdirectory(${CMAKE_CURRENT_LIST_DIR}/../../shared/haltz_proto haltz_proto)

add_executable(haltz_gpu src/main.c)
target_compile_options(haltz_gpu PRIVATE -Wall -Wextra)
target_link_libraries(haltz_gpu
    pico_stdlib pico_multicore
    hardware_spi hardware_dma hardware_pio hardware_pwm
    haltz_proto)
pico_enable_stdio_uart(haltz_gpu 1)
pico_enable_stdio_usb(haltz_gpu 0)
pico_add_extra_outputs(haltz_gpu)     # makes the .uf2
```
- PICO_PLATFORM is left at its default for rp2350, the Arm cores (rp2350-arm-s).
- Build type: Debug while stepping through code with the probe, Release for real speed (CMake Tools build variant).
- The Pico 2 W's on-board LED is wired to the wireless chip, not a GPIO. Link pico_cyw43_arch_none only if the LED is wanted; otherwise leave the wireless chip out.

## Pico 2 W #2 (debug probe)
No project. Download the debugprobe firmware for Pico 2 from Raspberry Pi's debugprobe releases, hold BOOTSEL while plugging in, drop the UF2 on the drive. Wiring: wiring-v1.md stage 6.

## tools/
Python 3 in a venv (tools/.venv), requirements.txt with pyserial to start. The tools parse the same .def files as the firmware.

## Rules for the shared code (so data interchange can't drift)
1. One source of truth: message IDs, cartridge layout and VM opcodes live only in shared/. Boards and tools include them, never copy them.
2. Plain C11 with fixed-width types (uint8_t, uint16_t...), no malloc, no ESP-IDF / Pico SDK / Arduino headers. Board-specific things (pins, UART/SPI drivers) stay in each firmware folder.
3. Never send a C struct with memcpy. Struct padding differs between compilers. Every message has pack/unpack functions that write bytes one by one, little-endian. Enums are never sent as enum types; they go on the wire as uint8_t.
4. X-macro .def files list each message once (name, ID, payload size). C expands them into enums, size tables and name strings; the Python tools parse the same lines.
5. Protocol version: proto.h has HALTZ_PROTO_VERSION. At boot every board sends HELLO (board ID, protocol version, git commit). The S3 shows a warning on the TFT if a board was flashed with a different version.
6. A breaking change to a message bumps HALTZ_PROTO_VERSION and means re-flashing all three boards.

## VS Code workspace
- haltz.code-workspace lists each project as its own root: cpu-s3, io-esp32, gpu-pico, plus shared, tools and docs. Don't add the repo root itself as an extra root.
- PlatformIO works on one project at a time: switch with the project environment switcher in the status bar, or open a file from that project.
- The Pico extension / CMake Tools handle the gpu-pico root. If the Pico extension misbehaves in the multi-root workspace, open firmware/gpu-pico in its own window; the shared code still works because it's linked by relative path.
- Editing shared/ files: the PC test build gives the editor a compile database for them.
- Workspace-level tasks: "build all", "flash cpu", "flash io", "flash gpu", "test shared", calling `pio run -d firmware/cpu-s3`, `pio run -d firmware/io-esp32 -t upload`, `cmake --build firmware/gpu-pico/build`, and the PC test build.
- upload_port and monitor_port set explicitly for each PlatformIO project.

## Order to set it up
1. Create the repo, root files and folder tree.
2. shared/haltz_proto with proto.h, packet.c, crc8.c and its PC tests; run them.
3. cpu-s3: check the module marking, then an empty app that prints the protocol version, flash size (16 MB) and PSRAM size (8 MB), and does a test file write while another task keeps reading PSRAM (proves XIP works).
4. io-esp32: template builds unchanged, then add the shared component and print the protocol version.
5. gpu-pico: hello over the probe's UART, printing the protocol version.
6. First real message: HELLO from io-esp32 and gpu-pico to cpu-s3.
